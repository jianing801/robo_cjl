## 一、已经确认的问题

### 1. 微调入口找不到当前正式结构库中的目标

- 位置：`shared_policy/joint_finetune.py:49`。
- 脚本固定寻找大腿0.25 m、小腿0.30 m、膝电机DM-J10010L-2EC、踝电机RS06。
- 当前 `configs/rough.json`、`backpack.json`、`amp.json` 使用各10档腿长网格。大腿在0.20–0.40 m、小腿在0.25–0.45 m等间隔取值，这两个目标腿长均不在网格上。
- 使用仓库真实 `select_grid()` 生成三份3000结构网格，精确匹配数均为0；执行真实 `joint_finetune.main()` 的选择分支，得到 `ValueError: Target exact design missing: stairs`。仅在复现中隔离了与此问题无关的计划文件哈希验证，没有执行物理环境。

**影响：按当前默认结构库，微调会在开始前退出。用户计划的“每个候选先微调，再评估结构”尚未接通。**

修复方向：显式传入真实候选结构key或ID，核对三任务的同一物理结构映射；不得静默换成最接近的网格结构。

### 2. 随机化评估可能把正确站立判成失败

- 位置：`shared_policy/randomization.py:23`、`shared_policy/pipeline.py:109`。
- robust命令允许站立，但基础成功规则仍无条件要求平均前进速度至少0.1 m/s，楼梯还要求净上升至少0.1 m。
- CPU反例：前9秒站立，再站9秒，最后2秒按0.2 m/s前进。机器人即使存活20秒且完全跟踪命令，平均前进速度也只有0.02 m/s，因此被判失败。
- 在当前8–10秒命令重采样规则下，连续三个站立段也是合法情况。对应的CPU采样反例已找到；这不代表已复现生产GPU种子的具体轨迹。
- 反方向也存在：全程站立命令下持续以0.11 m/s前进，可以通过当前基础步态门槛，尽管没有正确执行停步命令。

**影响：教师预检、跨轮选模和最终robust成功率都可能被错误计分。**

修复方向：将固定移动能力测试与包含停步的命令跟踪测试分开，或根据命令要求判断完成程度；不能沿用只适用于固定前进命令的门槛。

### 3. 首步摔倒会得到“零跟踪误差”

- 位置：`shared_policy/student_observations.py:66`、`shared_policy/pipeline.py:115`及`candidate_rank()`。
- 采集器排除终止重置步。如果机器人第一步结束回合，有效速度样本数为0；`TrackingError.values()` 用分母至少为1的保护，返回0。
- pipeline没有利用 `tracking_samples` 区分“没有有效样本”和“实际零误差”。
- CPU反例：两个候选其他任务结果相同、该任务都失败时，首步摔倒且RMSE为0的候选，可以排在坚持19秒才摔倒、RMSE为0.1的候选之前。

**影响：在成功率相同的候选之间，跟踪误差可能把更早失败的模型排在前面。不是所有排名都会反转，但该反例确定存在。**

修复方向：无有效样本应记录为缺失或无效，选模应同时考虑存活时长及失败，不允许空数据成为“最准确”的证据。

### 4. 蒸馏及微调的中断恢复没有完整接通

- 蒸馏：`shared_policy/pipeline.py:51` 在人工中断时生成 `USER_PAUSED`；`pipeline.py:261` 再启动时拒绝该标记；`start.py:540` 又拒绝为“蒸馏”使用 `--resume-paused`。
- 实际调用 `start.main(['蒸馏','--resume-paused','--dry-run'])`，得到参数错误 `--resume-paused仅用于资产准备或专家任务`。
- 普通报错后从已经完成的分片恢复，与手动暂停后恢复，是不同情形。此前“再次执行原命令恢复”的文字不适用于带暂停标记的共享蒸馏。
- 微调：`joint_finetune.py` 保存actor、critic和Adam状态，但没有读取这些状态的续训参数和路径；把 `ppo_007.pt` 当作 `--student` 输入会报 `Wrong student kind`。从单独actor重新开始会新建critic、Adam和更新计数，不能叫完整续训。

**影响：长时间运行被中断后，无法按当前公开入口正常接着训练。**

修复方向：提供明确的人工暂停恢复入口；微调区分“从actor开始新实验”和“恢复完整训练状态”，同时保持原计划和预算身份检查。

### 5. PPO任务请求存在并发读写错误窗口

- 位置：`shared_policy/joint_finetune.py:76`、`contract.py:20`、`ppo_channel.py:15`。

修复方向：临时文件完整写入并关闭后，再原子改名发布请求；读取方也应验证请求完整性。

## 三、实验设计上的薄弱环节

以下是需要对照实验判断的问题，不是已证明训练必然失败。

| 问题 | 当前证据与边界 |
|---|---|
| 每个结构每轮只保留32行，可能漏掉短时恢复动作 | robust楼梯每个训练分区可有1200行；18个工况分层后，每工况常只剩1–2行。在合成的1秒恢复片段复现中，单个环境约78–80%的采样种子没有保留任何恢复标签。不能据此断言真实机器人已丢失恢复能力 |
| 每轮先按所有课程数据的平均MSE筛掉其他epoch | 生产验证函数反例：候选A四轮误差为[0,0,0,1]，候选B为[0.4,0.4,0.4,0.1]，当前选A，尽管它在最终强度的误差高十倍。跨轮闭环只看到每轮的一个MSE候选，无法找回被筛掉的B |
| 代表性选择只有3个结构、单个种子 | 成本可控，但不足以证明全库均匀可靠，更不证明库外结构泛化；最后全库测试也只使用规定的单次种子 |
| 楼梯六档评估不是等权 | 8份环境按六档循环，计数为[2,2,1,1,1,1]。教师/学生仍成对比较，但简单总体均值更偏向前两档；论文应写实际权重或按工况另行汇总 |
| 基础步态通过不代表任务质量充分 | 目前基础门槛不要求跑步实际达到目标速度，也不衡量足够完整的楼梯通过、能耗或动作平顺性。速度RMSE虽有记录，最终通过标记没有对应的质量阈值 |
| 任意候选微调、微调后评分及实机接入尚未成为完整自动流程 | 当前微调脚本结束仅写 `requires_evaluation=True`；尚未自动完成候选微调后的独立评价。共享学生专用的实机观测构建、控制接口和验证也未在本次链路中完成 |

PPO还沿用原生RSL的超时补值近似：使用当前状态价值代替终止状态价值；这可能有偏差，但不是本轮新增问题。普通done处GAE切断、Gaussian原始动作logprob与裁剪执行的关系、PPO surrogate公式没有发现确证错误。不同任务的value目标尺度和共同梯度裁剪属于待实验评估的优化问题。

## 四、条件性的复现保护缺口

采集开始的audit计算一次源码协议哈希，结束保存data和summary时又按当时磁盘源码重新计算。如果采集中修改相关源文件，进程执行的旧模块可能被标成新源码身份。临时副本复现中，已导入函数仍返回0.35，磁盘函数已改成0.99，结束哈希却随磁盘变化。

该问题在训练期间源码保持不变时不会触发。修复应冻结启动协议供全部输出使用，并在结束时检查源码未变。另已核实：原生任务配置受到bank的source identity检查，不能笼统声称原生任务文件可以无提示地改动。
